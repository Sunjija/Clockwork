# 문지기 도트 제작 방식 수정 — 2026-09-30

## 요구를 잘못 적용했던 부분

사용자가 원한 것은 **동작별 기준 이미지를 먼저 생성하고, 애니메이션 프레임은 도트를 직접 편집해서 제작**하는 방식이었다. v0.2는 AI로 여러 자세가 든 시트를 생성한 다음 추출·양자화했다. 접지와 팔레트를 맞췄어도 이 제작 방식이 같아지는 것은 아니다. 이 문서는 그 오류를 인정하고 제작 경로를 교체한 기록이다.

현재 로더는 `ReturnV2/WardenAuthored`의 52프레임만 읽는다. 이전 `ReturnV2/Art/Warden`의 14프레임은 비교 이력을 위해 남아 있으나 재생하지 않는다. 배경과 소품은 단일 컨셉에서 도트화한 기존 결과를 유지한다.

## 실제로 다시 한 작업

1. `prototypes/tique-playground/Revisions/10/data.json`과 `Docs/process-history.md`를 확인했다. 티크의 대기는 원래 기본형 1프레임, 공격은 뒤쪽 팔 공격 12프레임인 최종 선택본이다. Unity에 있는 67 PNG와 시간을 원본과 대조했다.
2. 문지기의 **단일 기본 컨셉**을 알파 정리·32색·폭 136px로 한 번만 도트화했다. 192×144 투명 캔버스의 발 기준선 132px에 배치했다. 이것이 모든 프레임의 공통 원본 `base-native.png`다.
3. 같은 컨셉을 첨부해 물기 타격·돌진 준비·공중 다리 모음·경직의 **단일 참고 이미지 4장**을 생성했다. 다중 프레임이나 애니메이션 생성은 하지 않았다. 대기는 기존 기본 컨셉을 참고한다.
4. 참고 이미지를 눈으로 확인하고 동작의 주요 자세를 정했다. 픽셀 제작 스크립트는 참고 이미지의 픽셀을 읽지 않는다. 물기에서는 턱 닫힘, 돌진에서는 낮춘 몸과 발 지지, 낙하에서는 다리 모음과 착지 압축을 반영했다.
5. 기준 도트의 금속 외장·턱·발 픽셀 덩어리는 유지하고 정수 좌표로 편집했다. 몸체 변화는 최대 가로 3px·세로 4px, 공중 발 모음은 최대 9px다. 각 자세의 피스톤 연결과 턱 힌지 경계는 네이티브 픽셀로 다시 그렸다. 부위 회전, 매끈한 보간, 프레임별 리사이즈는 사용하지 않았다.
6. 프레임을 나란히 검토했다. 1차에서 보인 턱 아래 잔여 외곽선, 붉은 노심의 평면적인 색 변화, 앞다리 연결부의 튀는 밝은 픽셀을 수정했다. 노심의 원래 픽셀 무늬를 보존하고 앞다리 베어링을 연결한 뒤 다시 내보냈다.
7. 클립별 PNG·시트·APNG·Piskel·타이밍 JSON·변경 픽셀 목록을 저장했다. 변경 목록을 기본형에 다시 적용했을 때 PNG와 픽셀 단위로 정확히 같은지 검증했다.
8. Unity의 상태별 재생을 교체했다. 예고·가속·제동·착지·장갑 노출을 별도 구간으로 연결하고 실행 파일에서 확인했다.

이는 **코드로 명시한 픽셀 좌표 편집**이다. Piskel UI에서 마우스로 전 프레임을 그렸다고 주장하지 않는다. 편집 가능한 Piskel 파일을 함께 제공하므로 해당 도구에서 후속 수정을 할 수 있다. 기본 이미지와 동작 참고 이미지는 AI 생성이며, 중간 프레임은 생성 시트에서 추출하지 않았다.

## 티크와 동일한 프레임 기준

| 문지기 동작 | 티크 기준 | 프레임 | 원본 타이밍 합 |
| --- | --- | --- | --- |
| 기본 대기 | Idle | 1 | 1,000ms, 고정형 |
| 물기 / 충격파 발동 | Attack | 12 | 460ms |
| 돌진 / 제동 | Dash | 12 | 440ms |
| 점프 / 낙하 / 착지 | Jump | 15 | 800ms |
| 충돌 / 장갑 노출 / 복귀 | Attack 시간 배열 차용 | 12 | 460ms |

티크에는 문지기용 경직 클립이 없으므로 마지막 항목은 공격의 시간 배열을 차용한 별도 동작이다. 같은 프레임 기준이라는 말이 티크와 문지기의 크기·해부학·실루엣까지 같다는 뜻은 아니다.

- Attack / 경직: `20,30,40,30,70,30,40,40,30,30,40,60`
- Dash: `40,30,30,30,40,50,40,35,35,35,35,40`
- Jump: `60,30,40,40,90,70,60,40,70,60,35,35,45,45,80`

첫 프레임과 마지막 프레임은 모두 같은 기본형이다. APNG와 JSON은 가변 프레임 시간을 보존한다. Piskel은 티크 때처럼 **20FPS의 편집용 균등 재생**이며 정확한 게임 타이밍의 증거로 사용하지 않는다. APNG는 연속으로 같은 이미지인 노출을 합칠 수 있으므로 PNG/JSON의 프레임 수와 APNG 내부 청크 수가 다를 수 있다. 총 시간은 별도 검사한다.

## 게임 상태와 그림을 연결한 규칙

`Assets/Scripts/WardenAnimation.cs`가 그림 선택만 담당한다. 물리·피격 판정은 `ReworkModel`에 남아 있다.

- 돌진 예고: 0–2에서 준비한 뒤 2를 유지. 돌진 발동 시 3, 이동 중 4–6, 제동 때 7–11.
- 충격파: 예고 끝 30ms에서 3, 충격파가 실제 생성되는 순간 4. 이후 11까지 원래 시간대로 복귀한다. 강화된 두 번째 충격파도 타격 프레임부터 다시 재생한다.
- 낙하: 준비 0–2의 130ms 동안 접지한다. 이후 실제 공중 이동과 3–6을 연결하고 정점 자세를 유지한다. 하강은 7–9, 바닥에 닿는 즉시 10, 복귀는 11–14다.
- 장갑 노출: 경직 0–6 이후 열린 자세 6을 취약 시간 동안 유지한다. 취약 상태가 끝나면 7–11로 돌아온다. 노출 중 기본형으로 멋대로 돌아가지 않는다.
- 대기: 기본형 1장만 사용한다. 불필요한 몸통·머리 흔들림을 더하지 않았다.

보스의 예고와 반격 시간은 플레이 규칙에 따른 유지 구간이므로 APNG 한 사이클보다 길다. 프레임을 늘리거나 이미지를 변형해서 시간을 맞추지 않는다.

## 원본과 재현

저장소 루트 기준:

- `art/return-v3-manual/Source/base-native.png`: 잠근 기본 도트.
- `Source/base-provenance.json`: 단일 컨셉 원본과 도트 변환 기준.
- `Source/ActionReferences/*.png`, `prompts.json`: 동작별 단일 생성 참고 이미지와 요청문.
- `Clips/<동작>/<번호>.png`: 최종 네이티브 프레임.
- `Clips/<동작>/<번호>.pixels.json`: 기본형 대비 `[x,y,r,g,b,a]` 수정 좌표. 이 데이터만으로 최종 프레임을 재구성할 수 있다.
- `Clips/<동작>/<동작>.piskel`: 편집 가능한 시트.
- `Clips/<동작>/native.apng`, `preview.apng`: 원본 크기 / 최근접 3배의 가변 시간 미리보기.
- `Clips/<동작>/contact.png`: 자세 비교. `timing.json`: 노출 시간·포즈 파라미터.
- `QA/pixel-edit-audit.json`: 프레임별 바뀐 픽셀 수와 좌표 범위.
- `tools/art/author_iron_maw_pixels.py`: 픽셀 편집 정의와 내보내기.


## 검증 결과와 한계

- 기존 모델 검사 14개, 개편 모델 검사 8개와 일반 입력 엔딩 진행 통과.
- 문지기 상태·시간 조합 96,000회에서 유효한 프레임 선택. 충격파 발동=물기 4, 접지=낙하 10, 노출 유지=경직 6 검사 통과.
- 52프레임 전부 픽셀 수정 목록 재현 일치, Piskel PNG 재구성 일치, APNG 총 시간 일치, 티크 대응 시간 배열 일치.
- 공유 32색, 이진 알파, 접지 기준선, Point/밉맵 없음/무압축 검사 통과. 모든 프레임의 불투명 실루엣이 하나의 8방향 연결 영역임을 확인했다. 이것만으로 자세가 자연스럽다고 판정할 수는 없다.
- Unity 6000.5.3f1 Windows 수정본 빌드 성공. 1280×720 실제 창에서 일반 입력 자동 진행으로 퍼즐 3개→보스→엔딩 통과(53.46초, 체력 2/5, 장갑 파괴 3회). 이는 정답을 아는 자동 조작의 시간으로 예상 사용자 플레이타임이 아니다. 수정본 캡처 14장과 이벤트는 `QA/V3/Runtime720`에 별도 보존한다. 물기 타격·공중 다리 모음·노출 자세의 실제 렌더 캡처를 확인했다.

자연스러움과 캐릭터 디자인의 최종 승인은 사용자 검토가 필요하다. 기술 검사를 아트 품질 승인으로 표현하지 않는다. 티크 원본 자체는 변경하지 않았다.
